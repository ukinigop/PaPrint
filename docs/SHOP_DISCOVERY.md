# Shop discovery (local changes)

Shop cards now show a storefront illustration, the real number of accounts that saved the shop, and existing open/closed and price information. The detail screen has three selectable sample images: storefront, pickup counter, and printing area. All are bundled SVG placeholders labeled **Sample image**; they do not represent a particular business. Replace these with owner-supplied photos in a later photo-upload workflow.

**Most Bookmarked** sorts by distinct accounts bookmarking each approved shop, highest first. Duplicate IDs within an account count once. The bookmark icon is a separate 44-pixel button at the top-right of each shop photo, on cards and shop details; it does not open the shop or trigger the card animation. An outline means unbookmarked; a filled icon means bookmarked. Profile → Bookmarks lists the customer's bookmarked shops. Existing saved shops remain bookmarked without migration because the underlying savedShops data is preserved. Updates are serialized so quick taps on different shops cannot overwrite each other, then refreshed in the background to reconcile aggregate counts. Only the pressed button shows loading.

Card summaries use the format **2 bookmarks · 1 Ongoing Order · 7:00 AM - 8:00 PM**, with singular/plural wording and the owner's actual descriptive hours. Times with AM/PM retain their minutes, use uppercase periods and a spaced range separator. Missing hours remain explicit rather than invented.

**Nearby** requests foreground location only after selection and only if at least one shop has a map pin. It sorts by straight-line distance, with missing pins last. Device coordinates remain in screen memory, never uploaded to PaPrint or saved in the account. Permission denial, timeouts, and missing shop pins have explanatory messages. Selecting Nearby again retries a failed request. This is distance, not route length or travel time.

Owners choose their storefront with an interactive map: search an address or landmark, select a result, then tap the map or drag the pin to the entrance. Latitude/longitude update automatically and are shown as read-only values. New registrations require a valid map pin before submission and approval. Existing approved shops retain their data; those without pins are prompted to add one through the same approval workflow.

For approved shops, **Shop profile → Request location change** submits a proposed address and pin. Ordinary operating settings cannot write coordinates. The public pin/address stay unchanged while pending; duplicate pending requests return a conflict. Admins review current/proposed map locations under **Location change approvals**, then approve or reject (with a required reason). Approval atomically publishes the storefront address/pin; rejection preserves the old location and shows the reason to the owner. Decisions record requester/reviewer IDs, timestamps, previous location and outcome; conflicting decisions cannot both succeed. The legal registration address remains on file. Pending requests and review records never appear in public shop or order responses.

Customer shop cards and shop details show only the total ongoing orders using the existing refresh cycle. **Ongoing = Preparing + Printing**; the public interface hides the stage breakdown and ready-for-pickup count. Collected, Cancelled and Rejected are excluded. Owners retain their detailed order queue and stage counts. Customers still see the status of their own individual orders. Aggregate counts disclose no customer identities, document names or order contents, and do not claim a wait time or queue position.

Maps use locally served Leaflet controls, OpenStreetMap tiles and Photon address search (explicit Search button, bounded results, per-IP rate limit and one-hour in-memory search cache). The user approved these providers. Searches send the entered business address to Photon; map tiles disclose the viewed area to OpenStreetMap. `GEOCODER_URL` can point to a compatible private Photon instance. The public Photon service is best-effort, with [reasonable-use limits and no availability guarantee](https://github.com/komoot/photon#demo-server). Follow [OpenStreetMap tile policy](https://operations.osmfoundation.org/policies/tiles/): visible attribution, normal browser caching, origin identification, and no offline or bulk download. The map document sends only the application origin as Referer. Failed searches leave manual pin placement available. The picker uses a same-origin iframe on web and a WebView on native; use the full-stack local preview for web testing.

**Where is this shop?** opens Google Maps using the shop's pin when available, otherwise its name and registered address. Customers should confirm address-search matches when a pin has not been supplied.

The `expo-location` permission description and `react-native-webview` dependency require a fresh native build for installed Android/iOS applications. Web changes are included in the web export. This batch is local and has not been pushed or deployed.

Validation: backend integration coverage for save counts, privacy, required registration pins, owner/admin authorization, pending request and review races, rejected changes, queue status classification, map CSP/assets, address normalization/cache and provider failure. Frontend tests cover proximity order, missing/invalid pins, map query encoding, save counts and non-mutating sorts. Browser checks include live Photon search, loaded OpenStreetMap tiles, dragging with coordinate updates, owner submission, admin approval and the resulting customer address/queue. Device GPS, native WebView behavior and native permission prompts still require device verification.
